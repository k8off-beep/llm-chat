# LLM-чат: свободное общение, поиск подматриц и анализ продаж

Одностраничный чат с локальной LLM. Модель отвечает потоком (SSE), сама вызывает
инструменты: локальный поиск подматриц и SQL-запросы к базе продаж через FreePeak/db-mcp-server.
Всё работает на CPU, без внешних API и без Интернета.

## Состав

| Сервис | Что делает | Образ |
| --- | --- | --- |
| `web` | Apache раздаёт сборку React и проксирует `/api/*` в `agent`, включая SSE | `llm-chat-web:1.0` |
| `agent` | FastAPI + Uvicorn: чат, история, harness, локальный инструмент, MCP-клиент, отмена | `llm-chat-agent:1.0` |
| `llm` | llama-server (llama.cpp, CPU) с моделью Qwen3.5-2B внутри образа | `llm-chat-llm:1.0` |
| `db-mcp-server` | FreePeak/db-mcp-server, режим Streamable HTTP, доступ к БД только на чтение | `freepeak/db-mcp-server:1.14.0` |
| `postgres` | PostgreSQL с начальной базой продаж, именованный том `pgdata` | `llm-chat-postgres:1.0` |

```text
Браузер ──► web :8080 ──/api──► agent ──► llm (llama-server)
                                  │
                                  └──MCP──► db-mcp-server ──► postgres
```

Наружу опубликован только порт `web`. Остальные сервисы доступны только внутри сети Compose.
К PostgreSQL обращается только `db-mcp-server`.

## Быстрый запуск из готовых образов

Нужны Docker и Docker Compose v2. Интернет не нужен.

```bash
docker load -i images.tar
docker compose up -d
```

Открыть `http://localhost:8080`. Порт меняется переменной `WEB_PORT`.

Сервисы стартуют по очереди, с проверками готовности: `postgres` → `db-mcp-server`,
`llm` (загрузка модели) → `agent` → `web`. На стенде ниже от `up -d` до готовности всех сервисов
с пустым томом проходит около 45 секунд. `docker load` архива занимает около 50 секунд.

Состояние:

```bash
docker compose ps        # все сервисы, кроме web, должны быть (healthy)
docker compose logs -f agent
```

## Остановка и сброс базы

```bash
docker compose down      # остановить; данные БД сохраняются в томе
docker compose up -d     # запустить снова; данные на месте
```

> **Внимание: следующая команда удаляет все данные базы.**
> При следующем запуске база создаётся заново из `db/init/*`.

```bash
docker compose down -v
docker compose up -d
```

## Параметры

Все параметры заданы в `compose.yaml` со значениями по умолчанию, поэтому `.env` не обязателен.
Чтобы поменять значение, положите рядом файл `.env`, например `MAX_TOOL_CALLS=3`.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `WEB_PORT` | `8080` | порт web на хосте |
| `RUN_TIMEOUT` | `120` | предел времени одного выполнения, с |
| `MAX_LLM_CALLS` | `5` | обращений к модели за выполнение |
| `MAX_TOOL_CALLS` | `5` | вызовов инструментов за выполнение |
| `MAX_TOKENS` | `1024` | предел длины одного ответа модели, токены |
| `MAX_CONTEXT_CHARS` | `16000` | предел объёма контекста, символы JSON |
| `TEMPERATURE` | `0` | температура генерации |
| `MCP_TIMEOUT` | `10` | тайм-аут вызова MCP, с |
| `MCP_API_KEY` | `mcp_demo_key` | ключ FreePeak (демо) |
| `POSTGRES_PASSWORD` | `postgres_demo` | пароль суперпользователя БД (демо) |
| `ANALYST_PASSWORD` | `analyst_demo` | пароль роли `analyst` только для чтения (демо) |

Параметры llama-server (в `llm/Dockerfile`): `-c 8192 --jinja --chat-template-kwargs '{"enable_thinking": false}'`.
Режим рассуждений отключён: с ним модель на 2B зацикливалась и не укладывалась в лимит длины.

FreePeak запускается явно: `/app/server -t streamable -h 0.0.0.0 -p 9092 -api-key ...`.
Подключение: `read_only: true`, `max_rows: 100`, `query_timeout: 5`.
Встроенная в образ FreePeak проверка готовности обращается к порту 9093, который в режиме
`streamable` не открывается. Поэтому в `compose.yaml` она заменена своей проверкой на порту 9092.

При достижении любого предела пользователь получает понятное сообщение об ошибке.
Переполнение контекста не удаляет сообщения: агент отказывает и предлагает очистить чат.

## Аппаратные требования и стенд

Проверено на стенде:

- CPU: Intel Core i5-12400F (6 ядер, 12 потоков); Docker видит 12 CPU;
- память: 32 ГБ на компьютере, Docker Desktop (WSL2) доступно 15.5 ГБ;
- Windows + WSL2, Docker Engine 29.9.2, Docker Compose v5.6.1; образы linux/amd64.

GPU не нужен.

Время ответа (второй запуск подряд, через Apache, замер `.local`-скриптом по событиям SSE):

| Запрос | Первый фрагмент | Полное время |
| --- | --- | --- |
| Свободное общение: «Привет! Расскажи в двух предложениях, что ты умеешь.» | 0.4 с | 2.5 с |
| Поиск подматриц: контрольный пример | 4.6 с | 12.7 с |
| Продажи: «Покажи выручку по категориям за сентябрь 2026 года.» | 5.9 с | 9.3 с |

У запросов с инструментами первый фрагмент приходит позже: сначала модель формирует вызов
инструмента (это не текст), затем получает результат и только во втором обращении начинает писать ответ.
Первый запуск после старта отличался не больше чем на 0.3 с.

## Интерфейс

Одна страница: история сообщений, многострочное поле ввода (Enter — отправить, Shift+Enter — новая строка),
кнопки «Отправить», «Остановить», «Исправить и отправить», «Очистить чат» и строка состояния
(ожидание модели, генерация ответа, выполнение инструмента). Состояние сообщений, черновика и
текущего выполнения хранится в MobX-store (`web/src/store.js`).

- **Остановить** — отменяет выполнение на сервере (`POST /api/runs/{run_id}/cancel`).
  Полученный частичный ответ остаётся с отметкой «Остановлено».
- **Исправить и отправить** — доступно после остановки или ошибки. Последний вопрос
  возвращается в поле ввода, неудачная пара сообщений убирается из ленты. Отменённое или
  завершившееся ошибкой выполнение в историю сервера не записывается, поэтому повторный запрос
  уходит с историей, которая была до него.
- **Очистить чат** — отменяет текущее выполнение и забывает `conversation_id`.
  Следующий вопрос начинает новый диалог на сервере.
- Каждое событие несёт `run_id`. События, не относящиеся к текущему выполнению, игнорируются,
  поэтому запоздавшие события отменённого запроса не попадают в новый ответ и в очищенный чат.

Ответы модели отображаются как Markdown (`react-markdown` + `remark-gfm` для таблиц).
Произвольный HTML из ответа не исполняется: `react-markdown` не превращает его в элементы
(плагин `rehype-raw` не подключён). Неполный Markdown во время генерации разбирается заново
на каждом фрагменте и не ломает страницу.

## API агента

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/chat` | тело `{"message": "...", "conversation_id": "..." или null}`; ответ — поток `text/event-stream` |
| `POST /api/runs/{run_id}/cancel` | отменить выполнение; `404`, если оно уже завершено |
| `GET /api/health` | проверка готовности |
| `GET /api/ping`, `GET /api/conversations/{id}` | отладочные маршруты |

Если в диалоге уже идёт выполнение, `POST /api/chat` отвечает `409`.

События потока:

| Событие | Данные | Когда |
| --- | --- | --- |
| `start` | `run_id`, `conversation_id` | первым |
| `delta` | `run_id`, `text` | каждый фрагмент текста модели |
| `tool` | `run_id`, `name`, `status`: `running` (с `arguments`) или `done` | вызов инструмента |
| `done` | `run_id`, `status: completed` | терминальное: ответ готов |
| `cancelled` | `run_id`, `message` | терминальное: выполнение остановлено |
| `error` | `run_id`, `message` | терминальное: ошибка или достигнут предел |

Фрагменты текста отправляются браузеру по мере генерации llama-server. В Apache для этого
у `ProxyPass` включён `flushpackets=on`, а сжатие ответов не подключено.

## Как работает агент

Harness (`agent/app/harness.py`) — общий цикл для всех сценариев, без агентного фреймворка:

1. Модели передаются системная инструкция, история диалога и описания инструментов с JSON-схемами:
   локальный `find_submatrices` и разрешённые инструменты FreePeak, полученные через MCP `list_tools`.
2. Ответ модели читается потоком. Текст сразу уходит в браузер, а фрагменты `tool_calls`
   собираются по индексу до конца ответа и только потом выполняются.
3. Имя инструмента и аргументы проверяются на сервере. `find_submatrices` выполняется локально,
   `schema_sales`, `describe_sales`, `query_sales` — через MCP-клиент. Остальные инструменты FreePeak
   (`execute_sales`, `transaction_sales` и др.) модели не передаются и не выполняются.
4. Результат возвращается модели сообщением `role: tool` с `tool_call_id` её вызова.
5. Цикл продолжается до итогового ответа, отмены, ошибки или предела. Повторный вызов
   с теми же аргументами не выполняется, модель получает подсказку сформировать ответ.

Рабочие сообщения выполнения копятся в черновике и попадают в историю диалога только
при успешном завершении. Отменённое выполнение и его частичный ответ в контекст не входят.

Отмена: `task.cancel()` прерывает текущий шаг. Активный HTTP-запрос к llama-server закрывается,
и генерация в llama-server прекращается. Новые вызовы модели и инструментов после отмены не запускаются.
Отключение браузера отменяет выполнение так же. Контейнер продолжает работать, следующий запрос обслуживается.

Диалоги и реестр выполнений хранятся в памяти процесса Uvicorn и не переживают перезапуск.

Журналы (`docker compose logs agent`) содержат `run_id`, имя инструмента, аргументы (для продаж — SQL)
и результат:

```text
run_id=99d7e34d-... модель вызвала query_sales, аргументы: {"query":"SELECT COALESCE(SUM(s.amount), 0) AS total_revenue\nFROM sales s"}
result={'result': 'Results:\n\ntotal_revenue\n----\n128770.00\n\nTotal rows: 1', ...}
```

Пароли и ключи в журналы не выводятся.

## Защита базы от изменений

Модели не доверяется: на прогонах она иногда отправляла `DELETE` в `query_sales`.
Изменение данных останавливается на трёх уровнях:

1. агент: `query_sales` выполняется, только если запрос начинается с `SELECT` или `WITH`,
   иначе модель получает ошибку `read_only` и запрос в FreePeak не уходит;
2. FreePeak: подключение с `read_only: true`;
3. PostgreSQL: FreePeak подключается ролью `analyst` с правами только `CONNECT`, `USAGE` и `SELECT`.

## Поиск подматриц

`find_submatrices(matrix, pattern)` в `agent/app/submatrix.py`: матрица от 1×1 до 8×8,
строки одной длины, образец — квадрат N×N (1 ≤ N ≤ 8), символы `0–9`, `A–F`, `a–f`
(перед поиском приводятся к верхнему регистру). Результат: матрица, образец, размер,
количество и полный список вхождений `{row, column}` (с нуля, левый верхний угол).
При неверных данных возвращается структурированная ошибка, и модель просит исправить данные.

Итоговый ответ пишет модель по результату инструмента. Формат по умолчанию закреплён
в системной инструкции (`agent/app/prompts.py`).

**Обычный запрос:**

```text
Найди образец ["A1","B2"] в матрице ["A1A1","B2B2","A1A1","B2B2"]
```

Ответ (фрагмент):

````markdown
Исходная матрица:
```text
A1A1
B2B2
A1A1
B2B2
```
Искомая подматрица:
```text
A1
B2
```
Найдено вхождений: **4**. Координаты начинаются с нуля.
**Вхождение 1 — row=0, column=0:**
```text
A1
B2
```
…
**Вхождение 4 — row=2, column=2:**
```text
A1
B2
```
````

**Собственный формат:**

```text
Найди ["A1","B2"] в ["A1A1","B2B2","A1A1","B2B2"]. Верни только JSON со списком координат, без пояснений.
```

```json
[{"row": 0, "column": 0}, {"row": 0, "column": 2}, {"row": 2, "column": 0}, {"row": 2, "column": 2}]
```

**Ошибка в данных:** `Найди ["A1","B2"] в ["A1G1","B2B2"]` →
«Ошибка: Недопустимый символ 'G' в матрице. Пришлите, пожалуйста, исправленные данные.»

## База продаж

Таблицы `products(id, name, category)` и `sales(id, sale_date, product_id, quantity, unit_price, amount)`,
`amount` вычисляется как `quantity * unit_price`. Начальные данные: 8 товаров в 3 категориях,
32 продажи (июль — сентябрь 2026 и одна продажа 1 октября для проверки границы периода),
один товар без продаж. Скрипты: `db/init/01_schema.sql`, `02_data.sql`, `03_roles.sh`.

### Что модели дано в помощь

В системной инструкции: краткое описание двух таблиц, правила расчёта (выручка — `SUM(amount)`,
единицы — `SUM(quantity)`, полуоткрытый интервал дат) и два общих примера SQL.
Примеры построены на мае 2026 года: в базе нет продаж за май, и ни один пример не совпадает
с контрольными вопросами. SQL для каждого вопроса модель пишет сама, код его не подбирает и не подменяет.

### Эталонные запросы и ответы

Эталоны получены SQL-запросами в `psql` и сверены с ручным расчётом по `02_data.sql`.
Они используются только для проверки и в агенте не применяются.

**1. Какова выручка за сентябрь 2026 года?** — `36200.00`

```sql
SELECT SUM(amount) AS revenue
FROM sales
WHERE sale_date >= '2026-09-01' AND sale_date < '2026-10-01';
```

**2. Сколько единиц товаров продано за сентябрь 2026 года?** — `22`

```sql
SELECT SUM(quantity) AS units
FROM sales
WHERE sale_date >= '2026-09-01' AND sale_date < '2026-10-01';
```

**3. Назови три товара с наибольшей выручкой за сентябрь 2026 года.**
— Полка навесная `10500.00`, Зеркало прямоугольное `8000.00`, Зеркало-шкаф `6000.00`
(четвёртое место — `4800.00`, ничьей нет).

```sql
SELECT p.name, SUM(s.amount) AS revenue
FROM sales s
JOIN products p ON p.id = s.product_id
WHERE s.sale_date >= '2026-09-01' AND s.sale_date < '2026-10-01'
GROUP BY p.name
ORDER BY revenue DESC
LIMIT 3;
```

**4. Покажи выручку по категориям за сентябрь 2026 года.**
— Зеркала `18500.00`, Полки `10500.00`, Крючки `7200.00`.

```sql
SELECT p.category, SUM(s.amount) AS revenue
FROM sales s
JOIN products p ON p.id = s.product_id
WHERE s.sale_date >= '2026-09-01' AND s.sale_date < '2026-10-01'
GROUP BY p.category
ORDER BY revenue DESC;
```

**5. Покажи выручку по датам с 1 по 7 сентября 2026 года включительно.**
— 2026-09-01 `2500.00`, 2026-09-02 `3500.00`, 2026-09-05 `2000.00`, 2026-09-07 `3200.00`
(даты без продаж не выводятся).

```sql
SELECT sale_date, SUM(amount) AS revenue
FROM sales
WHERE sale_date >= '2026-09-01' AND sale_date < '2026-09-08'
GROUP BY sale_date
ORDER BY sale_date;
```

**6. Какова выручка за январь 2026 года?** — `0`, продаж нет.

```sql
SELECT COALESCE(SUM(amount), 0) AS revenue
FROM sales
WHERE sale_date >= '2026-01-01' AND sale_date < '2026-02-01';
```

### Результаты прогона

Каждый вопрос задан три раза, каждый раз в новом диалоге, через Apache, на поставляемой
конфигурации (`TEMPERATURE=0`, остальные параметры по умолчанию). Успешный запуск — реальный
вызов `query_sales` через MCP, правильные числа и соответствующее им объяснение.

| Вопрос | Успешно | SQL модели (пример) | Замечания |
| --- | --- | --- | --- |
| 1. Выручка за сентябрь | 3/3 | `SELECT COALESCE(SUM(amount), 0) AS total_amount FROM sales WHERE sale_date >= DATE '2026-09-01' AND sale_date < DATE '2026-10-01'` | — |
| 2. Единицы за сентябрь | 3/3 | `SELECT COALESCE(SUM(quantity), 0) AS units_sold FROM sales WHERE sale_date >= DATE '2026-09-01' AND sale_date < DATE '2026-10-01'` | — |

Числа совпали, потому что 30 сентября продаж нет. На предыдущем прогоне модель в этом вопросе писала `< '2026-10-01'`. |
| 4. По категориям | 3/3 | `SELECT p.category, COALESCE(SUM(s.amount), 0) AS revenue FROM sales s JOIN products p ON p.id = s.product_id WHERE s.sale_date >= DATE '2026-09-01' AND s.sale_date < DATE '2026-10-01' GROUP BY p.category ORDER BY revenue DESC` | — |

## Разработка

Окружение разработки — Dev Container (`.devcontainer/`): Python 3.12, Node 20 и доступ к Docker хоста.
В нём агент можно запустить с автоперезагрузкой (`uvicorn app.main:app --reload` в `agent/`),
а фронтенд — через Vite (`npm run dev` в `web/`, `/api` проксируется на `localhost:8000`).

Структура:

```text
agent/            сервис агента: app/ (main, harness, llm, mcp_client, tools, submatrix, prompts), tests/
web/              React + MobX + Vite, httpd.conf, Dockerfile
llm/Dockerfile    образ llama-server с моделью
db/               Dockerfile и скрипты инициализации PostgreSQL
models/           файл модели (не в git)
compose.yaml      пять сервисов поставки
```

## Известные ограничения

- Модель на 2B не всегда правильно ставит конец целого месяца: в вопросе 3 она писала
  `< '2026-09-30'` вместо `< '2026-10-01'` (см. результаты). Ответ совпал с эталоном только
  потому, что 30 сентября продаж нет. Исправлять SQL кодом нельзя по условиям задачи,
  поэтому ограничение оставлено и описано.
- Модель может попытаться изменить базу. Это всегда отклоняется (см. «Защита базы от изменений»).
- В режиме «свой формат» модель иногда возвращает весь результат инструмента в JSON вместо
  одного списка координат. Данные при этом точные.
- История диалогов хранится в памяти и пропадает при перезапуске `agent`.
